# План загрузки: первый кадр и обучающий облёт — 07.11.2026

**Статус: архитектурный план, не подтверждённая реализация.** Владелец: RocketTrip. Источник: актуальный `index.html`, `src/museum-startup.js`, `src/museum-onboarding.js`, `src/transport-bake.js`, `src/road-lod.js`, `src/steppe-surface.js`, `src/ukss-exhibit.js`. Не путать цель с уже измеренным результатом.

## Цель и критерий «готово»

Максимально рано показать **настоящую интерактивную, красивую панораму космодрома** (земля, реальная планировка, основные силуэты, ЖД/АД, свет, камера, базовое меню), убрать прелоадер и **запустить существующий прерываемый 26-секундный обучающий сценарий сразу после первого реального WebGL-кадра**. Всё остальное догружать по предполагаемому направлению камеры и по действию пользователя. Не делать 26-секундную задержку перед открытием; обучение — возможность загрузить дополнительные ресурсы на фоне, а не требование дождаться всех задач.

Целевые ориентиры, не гарантии: первый интерактивный кадр **2–4 с на быстром desktop**, **5–8 с на среднем мобильном**, начало тура **менее 1 с после показа**. Удерживать **не ниже 30 FPS** на мобильном и предпочтительно 45–60 FPS на desktop в экскурсии. Порог качества уточнить по реальному p75 из CI; не считать цифры достигнутыми без замера. Предыдущий отдельный GitHub Actions тест фиксировал ~24,8–25,3 с даже в fast mode 05.11; строгого синхронного A/B не было.

## Что сейчас держит критический путь

1. `index.html` загружает большой статический граф импортов (транспорт, 3D-модели, симуляции, редакторы, энциклопедические UI), прежде чем завершить `startup.ready()`.
2. До создания карты стоит `Promise.all` полного каталога и геоданных: `roads.geojson` ~1846 KiB, `railways.geojson` ~374 KiB, `river-water.geojson` ~271 KiB и другие наборы, даже если активен уже собранный far LOD.
3. `await loadUkssExhibit(ukssGroup)` в самом раннем ходе: GLB около 1196 KiB и декодирование. Весь космодром не должен ждать эту модель.
4. `await steppeSurfaceReady`: UV correction, снимки, базовые GPU-текстуры; основной DEM около 435 KiB также ожидается до открытия.
5. Полные `makeSite`, `installArchiveModels`, сложный `buildMuseumTerrainRelief`, инициализация событий/света/транспорта происходят до первого `animate(); startup.ready()`.
6. Сейчас уже существует быстрый транспортный кэш ~465 KiB gzip и авторский LOD ~92 KiB gzip, но `transportSourceFingerprint` и прочая сборка всё ещё могут зависеть от полного исходного JSON. Точный full detail при приближении создаётся на главном потоке, потенциально даёт «фриз».
7. Полная прелоадерная галерея (шесть слайдов) не должна конкурировать за ресурс, необходимый для первого кадра; при оптимизации нельзя снова ломать смену изображений.

## Новая критическая цепочка P0

`HTML/прелоадер + первый слайд → минимальное 3D-ядро → компактный boot-manifest с корректной схемой координат/камеры и ключевыми идентификаторами → низкодетальная земля с предварительной текстурой → far-меши АД/ЖД из готового LOD → облегчённые, но узнаваемые силуэты ключевых площадок + свет/туман → первый WebGL render → скрыть прелоадер → работающая камера и обучающий сценарий`.

- Создать **`boot-manifest`** (сценические координаты, идентификаторы, ссылки на LOD, карта приоритетов, версия и контроль сборки) и **`overview-pack`** (заранее собранные мини-меши/InstancedMesh площадок из утверждённых моделей, включая Гагаринский, 31, УКСС, 110, 112, Сатурн, аэропорты и город). Не выдумывать новые географические положения и дороги.
- До первого кадра не загружать исходные OSM дороги/ЖД, полную DEM, архив 3D-моделей, данные энциклопедии, самолёты, поезда и модели реконструкций. Для валидации кэша использовать атомарный **build manifest / SHA**, проверенный на этапе CI, а не обязательно весь сырой OSM на клиенте. Если мини-пакет отсутствует, понятный проверенный fallback, а не пустой экран.
- Использовать **предпросмотр спутниковой земли** (существующий preview JPEG ~116 KiB) или заранее подготовленный лёгкий общий атлас. Полные JPEG ~939 KiB / ~1084 KiB, грунтовые микротекстуры и детальную маску UV грузить после первого кадра. Подмена без шва/вспышки/заметного смещения.
- Самая первая видимая сцена должна быть законченной для выбранной стартовой камеры: контуры/рельеф, сеть главных дорог и ЖД, основные здания, вечерние огни как дешёвые эмиссивные объекты. Дальний промышленный силуэт не должен выглядеть как случайный набор крупных белых коробок.
- Учебные UI, камера, подсказки и кнопка «Пропустить» доступны без ожидания динамической карты знаний и сложных подсистем.

## Порядок загрузки после открытия

| Когда | Уровень | Содержимое | Почему |
|---|---|---|---|
| До первого кадра | P0 — блокирующее | 3D-ядро, обзорные земля/свет, готовый far LOD АД+ЖД, легчайший каталог площадок, стартовая камера, контурные модели и управление | Открывает правдоподобную живую карту |
| Тур 0–5 с: перемещение | P1 | Детали первой видимой области, легкие подписи, предзагрузка Гагаринского старта и его ближнего рельефа | Подготавливает будущий ракурс без конкуренции с первой отрисовкой |
| Тур 5–11 с: масштабирование | P1+ | `Гагаринский` / площадка 1, корректная геометрия стола, котлована, ближайших АД/ЖД; medium LOD только в области маршрута | У 11-й секунды камера летит к Гагаринскому |
| Тур 11–17 с: площадки | P1+ | Карточка Гагаринского, интерактивные указатели, локальная текстура и требуемые объекты для облёта | Пользователь видит объект близко, больше не нужен только силуэт |
| Тур 17–22 с: орбита | P2 | Данные и detail соседних видимых объектов; второстепенные модельки/фурнитура по бюджету кадров | Сохраняется плавный облет и отзывчивость |
| Тур 22–26 с: возврат | P2 | Medium LOD исходного общего ракурса; подходящие участки света/ландшафта. В конце вернуть **точный исходный ракурс** | Готовая обзорная сцена к самостоятельному исследованию |
| После тура и в паузах | P3 | Остальные территории по tile/LOD, станции и путевые знаки, более подробные огни, городки, полные контуры, HD-текстуры | Дозагрузка по расстоянию/видимости без «одной большой сборки» |
| Только при приближении/нажатии | P4 | Полная точная ЖД/АД на выбранном участке, детальные GLB, «Мрия», ТУА, полёт/поезд/машины, пусковые анимации, видео/энциклопедия/история | Не грузить всё на каждый визит |

**Важное условие:** обучение добровольное. Для повторного посещения, `?tour=0`, прямых ссылок `?view=...`, reduced motion или немедленного «Пропустить» нельзя ждать фиктивных 26 секунд. В этих случаях выбранный объект и актуальный фрустум камеры сразу повышают приоритет соответствующего пакета.

## Планировщик ресурсов

- Отделить **скачивание**, **декодирование/геометрию** и **GPU upload**. Текущий `startup.defer` ограничивает число задач, но долгий JS внутри задачи способен заморозить главный поток.
- Приоритет по событию: явный выбор **100** > следующий ракурс тура **90** > видимые объекты **70** > соседние видимые тайлы **50** > дальние **20** > неиспользуемый архив **5**.
- Сканировать `frustum` и траекторию обучения наперёд. Для свободной камеры приоритет пересчитывать по позиции/высоте; не гоняться за каждым движением камеры (debounce/устойчивая приоритизация).
- Одна тяжёлая CPU-декодировка за раз; скачивания на обычной сети до 2–3 одновременно, при `saveData`/2G — 1. GPU добавлять небольшими чанками в паузах кадров. Основные геометрические преобразования — Web Worker / офлайн-генератор, иначе нарезать на короткие порции.
- При падении FPS приостанавливать несущественные задачи и отменять ещё неиспользуемые дальние запросы; при нажатии «Пропустить» мгновенно переключать приоритет на текущую камеру.
- LOD меняется без скачков положения, геометрия новых и старых дорог следует тому же авторскому фильтру (18 добавлений, 286 удалений и более новые правки), ЖД-переезды/станции не «возвращаются» к старой геометрии.
- На видимом объекте сразу показывать lightweight anchor и карточку, включая состояние загрузки деталей/повтор при ошибке; нельзя блокировать поворот/зум из-за ожидающего GLB.

## Что и как делать по этапам

1. **Базовый замер и точные события.** На одинаковом холодном/тёплом кэше снять Waterfall + Performance: CSS/JS evaluation, большой `Promise.all`, `loadUkssExhibit`, создание площадок, DEM, фактический WebGL first render, начало тура, p75 FPS. `first-frame` до reveal не подменять реальным моментом render.
2. **Тонкий bootstrap и отдельный P0-бандл.** Увести тяжёлые статические импорты в `import()` по требованию; создать неизменяемый low scene pack + атомарный manifest; исключить загрузку OSM/GLB/DEM из пути к первому кадру.
3. **Ранний `ready()` и Tour Look-Ahead.** Убрать `await loadUkssExhibit`, `await steppeSurfaceReady`, build all sites и DEM из gate; заменить P0-заместителями с точной позицией. К 11-й секунде загрузить реальные нужные данные Гагаринского. Сохранить выход из прелоадера без искусственной задержки; не менять 26 сек и право прервать.
4. **Тайл-загрузка поверхности и транспортных мешей.** Дальние тонкие линии и предварительные материалы видимы сразу; road/rail full detail строить в worker/на этапе CI и загружать по зонам, а не всем объектом. Заменять только активный сегмент, не ломая train/road routes, source IDs, редактор, указатели и подсветку.
5. **Отложенные впечатления.** Включать дополнительные световые эффекты, самолёты, автомобили, поезда, ЖД-станции, ракетные GLB и цифровые реконструкции только по видимости или явному действию. Энциклопедию загружать при открытии главы, а не целиком.
6. **Очередь и защита.** Отдельные бюджеты CPU/GPU/сети, abort/fallback/timeout, версия assets, тест на повторный визит и на пустой/устаревший кеш.

## Прелоадер

- Первую картинку загружать приоритетно. Остальные **пять** подгружать заблаговременно к своему показу, без конкуренции с P0.
- Нельзя просто заменить все `src` на `data-src`: ранее это делало галерею неполной. Реализация должна выполнять `ensureImageReady` для следующего слайда с проверкой `load`/`error` и запасным слайдом. Все шесть изображений сохраняются.
- Первое фоновое изображение текущего ракурса можно использовать как статичную визуальную подложку **только пока запускается WebGL**, но нельзя выдавать его за интерактивную карту.

## Проверки и критерии приёмки

- Сквозные `performance.mark`: `bootstrap-start`, `overview-data-ready`, `first-webgl-draw`, `first-interactive-frame`, `preloader-hidden`, `tour-start`, `tour-gagarin-ready`, `tour-end`, `tile-ready` (каждый класс чанка); отчёт по размерам запросов и сумме долгих задач.
- GitHub Actions cold/warm: desktop + средний Android с эмуляцией сетей и реальным `?tour=1`. Проверять интервал первого кадра, кадры во время облёта, правильную высоту и ракурс после возврата, весь функционирующий UI, 3D-переключения, непрерывность АД/ЖД, отсутствие пропавших объектов, graceful fallback при ошибке части файлов.
- Не прогревать весь GPU в начале тура. Фиксировать P75/P95 FPS и всплески main-thread задачи >50 мс.
- Первая реальная панорама должна быть **не только быстрой, но и визуально достоверной** — при приближении не появляются скачком большие неверные силуэты, вырезанные дороги не возникают вновь.
- Шаги принимать последовательно по независимым CI и экранным снимкам, не утверждать успешную оптимизацию только по деплою GitHub Pages.
